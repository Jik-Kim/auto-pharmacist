## ⚠️ 어떤 스쿱으로 쟀는지 반드시 적는다

**2026-09-21 의 material_1·2·3 측정은 전부 `scoop_1`(전용 스쿱 1번) 으로 떴다.** 자세만 바꾸고
스쿱은 고정했기 때문에 "자세가 원인" 이라는 결론이 성립한다 — 스쿱이 교란 변수가 아니었다.

하지만 **운영 조합은 원료통마다 전용 스쿱이 짝지어져 있다** (`stations.yaml`, 9/18 확정):

| 원료통 | 전용 스쿱 | `expected_scoop_width_mm` | 파지부 (9/21 사용자 확인) |
|---|---|---|---|
| material_1 (원료 A) | `scoop_1` | 15.5 | 원본 그대로 |
| material_2 (원료 B) | `scoop_2` | 18.0 | 종이테이프를 감아 두껍게 |
| material_3 (원료 C) | `scoop_3` | 28.0 | 보드롱을 붙여 두껍게 |

**세 스쿱은 같은 물건이고 파지부 두께만 다르다 — 무게는 셋 다 32 g 으로 같다.** 폭 지문
(`WRONG_TOOL` 판정)을 만들려고 테이프·보드롱으로 두께만 바꾼 것이다. 따라서 **보정값을 스쿱마다
따로 잡을 필요가 없다** — 무게도 무게중심도 같으므로 offset·gain 을 공유할 수 있다.

실제로 material_3 에서 scoop_1 과 scoop_3 의 Mx·My 가 똑같이 0 으로 나왔다 (아래 결과표).
**material_3 의 안정성은 자세의 성질이지 스쿱 조합의 성질이 아니다.** Mz 만 0.136 → 0.170 으로
다른데, 파지부 두께가 달라 그리퍼가 다른 지점을 무는 탓으로 보이고 Fz 에는 영향이 없다.

> **⚠️ A·C 에게 알릴 것** — 보드롱은 눌리는 재질이다. 그리퍼가 `gripper.force_n` 20 N 으로 물면
> 두께가 줄어들 수 있고, 그만큼 폭 지문 판정(`fingerprint_tolerance_mm` 1.0 mm)이 흔들린다.
> 종이테이프도 정도는 덜하지만 마찬가지다. 실측으로 확인할 문제이며 도징 소관이 아니다.

## 페이즈 구성

한 페이즈 = **무게 한 점 × 5회 측정**(회차마다 표본 10개). 약 45초 걸린다.

| 페이즈 | 무게 | 구성 (9/21 실측) | 목적 |
|---|---|---|---|
| 0 | 빈 그리퍼 | — | `reset_workpiece_weight` + 기준값 — 영점 그 자체. 도구가 자동으로 찍는다 |
| 1 | 32 g | 빈 스쿱 | 영점 직선의 첫 점 |
| 2 | 83 g | 원료 51 g + 스쿱 32 g | 두 번째 점 — 여기까지면 gain 직선이 선다 |
| 3 | 133 g | **원료 100 g** + 스쿱 32 g | 세 번째 점. 잔차가 의미를 가지려면 3점이 필요하다 (`calib.fit_gain` 경고) |

3번 점은 원료 100 g — **레시피 C 의 목표량과 같다.** 즉 이 점의 흩어짐이 곧 실제 운영에서
100 g 을 계량할 때의 흩어짐이다. 원료는 실물을 담아서 잰다.

무게는 매번 **실제 저울로 재서** `--actual-g` 에 넣는다. 눈대중 값을 넣으면 그게 그대로 offset 오차가 된다.

## 실행

터미널 1 — 로봇 + 그리퍼 드라이버 (`cell.launch.py` 아님, skill_node 가 로봇을 잡으면 안 된다):

```
source tools/env.sh && ros2 launch m0609_rg2_bringup new_bringup.launch.py mode:=real host:=192.168.1.100
```

터미널 2 — 페이즈 1 (빈 스쿱, 영점 포함). 첫 페이즈만 `--goto-station` 과 영점을 잡는다:

```
source tools/env.sh && python3 ros2_ws/src/gmp_dosing/calibration/measure_g1.py \
    --actual-g 32 --object scoop --goto-station material_1 --gripper \
    --sets 1 --trials 5 --samples 10 --period 0.1 \
    --out records/g1_rezero_0921_material1.csv
```

페이즈 2·3 — **같은 파일에 이어 쓰고, 영점은 세션에 한 번만 잡는다** (`--no-reset`). 자세도 그대로 유지:

```
source tools/env.sh && python3 ros2_ws/src/gmp_dosing/calibration/measure_g1.py \
    --actual-g <저울로 잰 값> --object scoop --gripper --no-reset \
    --sets 1 --trials 5 --samples 10 --period 0.1 \
    --out records/g1_rezero_0921_material1.csv
```

요약:

```
python3 -m gmp_dosing.core.calib records/g1_rezero_0921_material1.csv --method tool_force
```

**그리퍼는 언제나 Enter 를 누른 뒤에 열린다** — 세트를 시작할 때도, 측정이 끝날 때도 그렇다.
바로 열면 원료가 담긴 스쿱을 떨어뜨린다. 받치고 누르면 되고, 이미 비어 있으면 그냥 Enter 다.
세트 도중 Ctrl-C 는 측정 중단으로 그대로 전달되며, 마지막 정리 프롬프트에서 Ctrl-C 를 누르면

gain 불확실성은 양 끝점(32 g·133 g) 회차 평균의 표준오차(σ/√5)를 무게 범위 101 g 으로 나눈 값이다.
두 gain 의 차이 0.282 는 합성 불확실성 0.119 의 2.4배라 잡음만으로 설명하기는 어렵지만,
**세트가 1개라 다시잡기 오차가 통째로 빠진 낙관적 추정이다** — 폐기 전 데이터에서 세트 간 흐름이
7.9~8.6 g 였으니 그것까지 넣으면 두 값의 구간이 겹친다. 어느 쪽이든 결론은 같다:

- 자세 의존이 진짜라면 → 자세마다 보정값이 따로 필요하다 (운영에서 원료통 3개를 다르게 다뤄야 한다)
- 잡음이라면 → 잡음을 줄이기 전에는 무엇을 재도 gain 이 안 나온다

**어느 쪽인지 가리기 전에 보정값을 확정하면 안 된다.** 각 점의 offset 흩어짐(23~30 g)이 그 점들의
3σ(19~52 g) 안에 통째로 묻혀 있다 — 직선의 기울기가 잡음에서 나온 것인지 신호에서 나온 것인지
지금 데이터로는 가릴 수 없다는 뜻이다.

**자세에 따라 안정성도 다르다** — material_2 의 회차 평균 σ 가 material_1 의 2.5배다(17.3 vs 6.9 g).
material_1 이 더 안정적이었다.

저주파 요동 위에 올라탄 표본들은 서로 같은 방향으로 틀린다.

**그런데 계량 창이 정확히 한 주기다** — 10표본 × 0.82초 = 8.2초. 진동을 한 번만 훑으니

운영 계량은 `scale.samples` 20 × 0.82초 = 16.4초로 2주기를 훑어 조금 낫지만 문제는 같다

### offset 은 tare 가 소거한다 — 판정에 쓰이는 것은 gain 뿐

`gain 1.03 · offset 195` 로 환산하면 10표본 세션들은 오차 −0.77~+0.61 g 로 맞는데 20표본 세션만
+4.71 g 어긋난다. 그 세션의 offset 이 190.8 이어서다 (다른 세션은 191.8~197.4).

그래도 **도징 판정은 영향을 받지 않는다**:

```
gross = raw_g × gain + offset,   tare = raw_t × gain + offset
scooped = gross − tare = (raw_g − raw_t) × gain        ← offset 이 소거된다
```

`process_fsm` 이 `SCOOP_TARE` 에서 그 파지 상태의 빈 스쿱을 재 tare 로 쓰고, VERIFY 의 용기 순량도
같은 구조다. `offset_g` 는 `gross_g` 표시·기록용 대략값이다. `test_offset_cancels_out_in_net_weight`
가 이 성질을 고정한다.

## 걸리면 여기부터

**아무 출력 없이 멈춘다** (`_robot_id` / `_robot_model` / `_srv_name_prefix` / `_topic_name_prefix` 네 줄만 찍히고 정지)
— 브링업을 띄우자마자 실행해서 `dsr_controller2` 가 아직 활성화되기 전이다. `DSR_ROBOT2` 의 조회·설정 함수는
`wait_for_service` 없이 `call_async` 부터 하고 기다리므로, 컨트롤러가 없으면 future 가 끝나지 않고 조용히 선다.
Ctrl-C 로 끄고 컨트롤러가 뜬 뒤 다시 실행한다. 확인:

```
ros2 control list_controllers -c /dsr01/controller_manager     # dsr_controller2 가 active 여야 한다
```

2026-09-21 에 실제로 걸려서 `measure_g1.py` 에 준비 확인(`wait_controller`)을 넣었다 — 이제는 30초 기다린 뒤
무엇이 문제인지 말하고 끝난다(`--controller-timeout` 으로 조절). 멈춰 있으면 그 버전이 아닌 것이다.

**`컨트롤러 준비 확인` 까지 찍고 멈춘다** — Ctrl-C 로 끄고 곧바로 다시 켰을 때 생긴다 (9/21 실제로 겪음).
노드가 ROS 그래프에서 빠지는 데 시간이 걸려, 같은 이름(`gmp_dsr_client`)으로 바로 다시 붙으면 이전 세션
잔여물과 꼬인다. `wait_controller` 는 새로 만든 클라이언트로 확인하므로 통과하지만 `DSR_ROBOT2` 내부
클라이언트가 걸린다. **끄고 5초쯤 두었다가 켠다.**

**`The passed service type is invalid`** — `ros2 service call` 을 쓸 때 `dsr_msgs2` 가 안 잡힌 것이다.
`source tools/env.sh` 로 ws_dsr 언더레이까지 올린다 (`ROS_DOMAIN_ID=70` 도 여기서 설정된다).

- **회차 내부 σ p95** — `max_std_g` 의 바닥. 이보다 낮게 잡으면 정상 계량이 `valid=false` 로 떨어진다.
